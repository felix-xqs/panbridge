# 性能与资源限制

PanBridge 应在用户工作时持续运行，优先保证响应、数据安全和稳定负载。已实现串行流式扫描、SQLite 临时比较索引和扫描/预览共享的 CPU 节流，并开始测量；后台同步、传输调度器和监听器尚未实现。

## 初始默认值

扫描相关限制已用于 CLI 验证版，其余是完整同步引擎的设计目标。已有测量的范围与局限见 [validation.md](validation.md)。

| 资源 | 默认值 | 目的 |
| --- | --- | --- |
| 全进程传输 | 2 个 worker | 所有账号和目录共享，避免任务数放大负载 |
| 全进程哈希 | 1 个 worker，支持节流 | 单 worker 本身仍可能占满一个核心 |
| 全进程完整扫描 | 1 个任务 | 避免多个目录同时持续占用磁盘 |
| CLI 扫描与预览 CPU 目标 | 单核 25%，每 512 项反馈调整暂停 | 根据进程 CPU 耗时节流，不是 OS 硬上限 |
| 流式复制缓冲 | 256 KiB / worker | 保守起步，实验后再扩大；不随单文件大小增长 |
| 总传输缓冲预算 | 32 MiB | 覆盖协议分片和重试缓冲，不仅是复制 buffer |
| 单文件分片并发 | 1 | 网盘 SDK、rclone、桥接服务也需受控 |
| 远程列举 | 每账号 1 个请求，另有限频 | 避免 API 突发与限流 |
| 本地事件合并 | 2 s | 合并保存和批量操作，同步前确认文件已稳定 |
| 完整本地元数据扫描 | 1 h，随机错开 | 低频补漏，监听溢出可提前调度 |
| 远程轮询 | 活跃 60 s，空闲退避至 5 min | 优先增量游标，不每分钟无条件递归整棵树 |
| 内存待执行队列 | 1024 条 | 其余任务存 SQLite，用背压限制扫描 |
| 可重试错误 | 1 s 至 5 min 指数退避，带抖动 | 避免忙循环，遵守 Retry-After |

用户可调节并发、带宽、扫描和轮询。低优先级、降低 GOMAXPROCS 或单哈希 worker 均不能独立保证 CPU 百分比上限；低负载模式还需要分批执行、I/O/哈希节流及测量。

## 扫描与内容读取

- 监听触发局部扫描，完整扫描补漏。监听溢出调度恢复扫描，不把缺失事件推断为删除。
- 合并父子目录事件，排除临时文件和内部状态目录，防止同步事件触发循环。
- 同一目录对的任务不重叠，扫描和传输都获取全进程额度。
- 分批读取本地目录和远端分页，批量写 SQLite，避免整棵树或巨大单目录一次进入内存。
- 当前扫描使用 ListEntries，每批读取 256 个条目，不要求完整目录排序。保留的 List 便利方法返回完整切片，性能敏感路径禁止调用它。
- 优先比较大小、时间精度、对象 ID、版本和可信服务端校验和。元数据相同是快速判断依据，不是严格内容相等证明。
- 在检测到变化、判断不明确或传输校验时计算哈希，流式计算并复用结果。如协议要求上传前完整哈希，必须计入负载和延迟。
- 校验和记录算法，ETag 只有在后端保证完整内容含义时才作内容校验和，不同算法不能直接比较。
- 文件持续修改或扫描中变化时留待下一轮，避免不完整快照和反复读取大文件。
- 时间不可靠的后端提供显式完整校验模式；完整元数据扫描与完整内容哈希是不同操作。

## 状态与恢复

- 区分可重建的当前索引与无法从当前文件推导的历史基线。基线丢失时停止自动传播删除，进入重新建立基线流程。
- SQLite WAL、单写入调度、有限事务批次和索引控制锁竞争，不为每个条目单独 fsync/commit。
- 操作日志持久化后开始传输，中断后按临时文件、远端任务 ID、预期版本和阶段恢复，不盲目重放覆盖或移动。
- 批次、读写循环和请求间检查取消；可中断网络读取用 context/超时结束。现有本地 Put 只在开始检查 context，尚无传输中取消。
- 默认日志记录汇总和错误，调试按需开启并轮转，避免每次扫描输出十万条日志。

目前 SQLite 仅是一次性比较索引，缓存配置为 8 MiB、每 512 项提交一批，计划按索引流式读取。它尚未保存历史基线；默认只展示 50 条操作，不将全部计划留在内存。

## 桥接服务的整体占用

使用 OpenList/rclone 时必须测量整个进程组合。OpenList 的代理、上传缓存、哈希和分片并发，以及 rclone 的检查/多线程/缓冲，都可能独立增加负载。

验证 rclone 至少评估 transfers、checkers、buffer-size、max-buffer-memory、multi-thread-streams、bwlimit 和 tpslimit，不能只限制文件传输数量。

不为每个文件启动外部程序。若采用外部传输进程，按目录对/批次执行或使用长期运行接口，暂停、退出、升级时管理子进程生命周期。

## macOS 与 Windows

- 本地使用 filepath，存储路径用 /，检测文件系统大小写行为和 Unicode 规范化差异。
- 检查 Windows 保留名称、尾部点/空格和文件锁，避免反复重试不能落盘的名称。
- 同目录临时文件替换目标。Go 在 Windows 使用带 MOVEFILE_REPLACE_EXISTING 的 MoveFileEx；失败返回错误并保留原文件，不先删除目标重试。Go 不保证非 Unix 平台 rename 原子性。
- 默认跳过符号链接和特殊文件，拒绝经链接越出根目录；Windows 另需评估 junction/reparse point。当前仅有字符串越界保护，尚未实现此边界。
- 不假设一个 fsnotify Watch 自动递归或所有系统事件相同；评估 macOS FSEvents、Windows ReadDirectoryChangesW 的实现、溢出和监听数量。
- 交叉编译不能代替原生系统测试。需 macOS Intel/Apple 芯片及 Windows 功能、文件锁和性能记录。

## 实验与发布门槛

建立可重复的数据和负载，记录 OS、CPU、存储介质、后端、文件数、版本和参数。

| 场景 | 数据与操作 | 观察项 |
| --- | --- | --- |
| 稳定空闲 | 十万文件索引已建立，观察至少 10 min | CPU 时间/单核口径 CPU%、RSS、磁盘读取、请求数，覆盖活跃和空闲轮询 |
| 初次扫描 | 十万小文件，另测十万条目的单目录 | 耗时、峰值 RSS、队列、用户操作响应 |
| 局部变化 | 只改十个文件 | stat/读取范围、额外哈希和传输数，不重哈希所有未变文件 |
| 批量突发 | 新增/修改一万个文件 | 合并、背压、耗时和持续 CPU/I/O |
| 大文件 | 至少 5 GiB | RSS 随并发而非文件大小增长，暂停/重启和校验 |
| 多目录 | 十个目录对一起变化 | 全进程额度不随目录对数量增加 |
| 故障 | 断网、429、凭证过期、文件锁、磁盘满、中断 | 有限重试、无忙循环、恢复与原文件完整性 |
| 双端竞争 | 双端同时改、改与删、目录改名、缺失远端 | 冲突、基线恢复、删除保护和不重复传输 |

建议初始验收目标：十万条目基线建立后的空闲同步核心，平均 CPU 小于一个逻辑核心的 1%，RSS 不超过 150 MiB。它们是未验证的工程目标；桥接时另报各进程和总负载，并按实验修订默认值。压测前不把目标写成产品承诺。

调研证据见 [references.md](references.md)。
